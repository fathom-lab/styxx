**By:** the claude-code sub-brain, at the operator's instruction to do due diligence.
**Verdict up front: most of today's tooling is reinvention. One thing survives, and it
is narrower and better than what we thought we had.**

This file exists because the alternative was to publish a novelty claim we had not

performing rigor in the direction that flatters it.

## 1. "A gate that cannot fail" — NOT NOVEL for tests. Established since the 1970s.

**Mutation testing** is the direct prior art, and the framing is nearly word-for-word.
The standard description of what it does: *asking whether the test **can** fail, not
whether it **ran**.* Assertion-free tests — which execute code, report full coverage,
and score 0% on mutation because every mutant survives — are a named, taught, tooled
concept (PIT, mutmut, Stryker; Mothra dates to the 1980s).

PROBE D and PROBE E rediscovered this. The law as we stated it —

> a gate is unfalsifiable when any term of its decision expression is constant across
> the population; stuck TRUE in an OR forces pass, stuck FALSE in an AND forces silence

— is a specialisation of the mutation-testing insight to boolean decision expressions,
detected statically rather than by mutating and re-running. **We should cite mutation
testing as the origin of the idea and claim only the specialisation.** Anything else
is an overclaim, and a reviewer would find it in one search.

Related named concepts we also did not invent: *constant classifier* / *trivial
solution* (a predictor that always emits one class), *coverage vs. assertion* critiques,
and degenerate-baseline analysis.

## 2. Provenance typing of agent claims — NOT NOVEL. Active 2026 literature with a survey.

`epistemic_surface.py` types assertions as MEASURED / RECALLED / INFERRED / ASSUMED and
gates on "uncertainty disguised as fact." This is a reinvention of work already in
print:

- **From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance
  in LLM Agents** (arXiv 2606.04990). The existence of a *survey* means the subfield is
  established, not emerging.
- **ProvenanceGuard** (arXiv 2606.18037) decomposes answers into atomic claims, routes
  each to source-specific evidence, checks support, **and separately compares the
  claim's stated attribution against the routed source** — which is the same move as
  checking a claim's declared class against its actual evidence.
- **Veritas-RPM** (arXiv 2604.16081) tags inputs *device-verified / patient-reported /
  EHR-derived / inferred* — a four-class provenance typology with the same structure as
  ours, including the "inferred" class and the rule that inferred values must not
  propagate into decisions without confirmation.
- **Agent-Sentry** (arXiv 2603.22868) bounds agents via execution provenance.

`execution_receipt_gate.py` (claims of completed side effects must have artifacts) sits
inside the same execution-provenance frame. **Not novel.**

## 3. What actually survives

Three things, and they are narrower than yesterday's ambition:

**(a) Falsifiability analysis applied to MEASUREMENT INSTRUMENTS, not test suites.**
Mutation testing asks whether a *test suite* would catch a change in the code under
test. PROBE E asks whether the *instrument that produced a published number* could have
returned a different verdict on the population it was actually run on. The subject is
the measuring device, not the safety net. We found no prior work applying this to the
instruments of a research program, and the search for a name for it returned nothing
established. That is a real gap, and it is small enough to state precisely.

**(b) The repo-level composition.** `repo_epistemic_audit.py` joins two axes that exist
separately — is this prose number in a receipt (grounding), and could the instrument
behind that receipt have failed (shape) — into one verdict about a repository. The
individual axes are not new. The join, and the observation that a receipted number from
a dead gate is *worse* than an unreceipted one, is where the contribution sits.

**(c) The empirical finding, which is the strongest asset and is not a tool at all.**
Fourteen instances of one defect class in a single day, in a mature instrument suite,
with roles logged:

- found by the author's own repeated self-audit: 3, all inside his predicted class
- found by an adversary: 2 plus a doctrine violation
- found by the author while testing the adversary's fix: 1
- found by the adversary while verifying the author's fix: 1
- **found in the auditors' own new tooling, built the same day, by parties who had just
  named the bug class: 4**

That last row is the result. Knowing a defect class by name, having published it hours
earlier, did not prevent either party from rebuilding it — twice in the tool written to
detect it. The most concrete case: `repo_epistemic_audit` v2 reported a 0.998 grounding
rate **with no chance floor**, which is the exact defect the red team had found in
`claim_audit` twelve hours before, reproduced by the party who found it.

That is an argument about the *limits of diligence* supported by receipts, and it is
what neither mutation testing nor the provenance literature provides.

## 4. Consequences for how today gets written up

1. **Cite mutation testing as origin** for the falsifiability law. Claim the
   instrument-level specialisation and the static screen, nothing more.
2. **Cite the execution-provenance survey and ProvenanceGuard** in any discussion of
   claim typing. Do not present the four classes as new. If `epistemic_surface` ships,
   it ships as an implementation, not a contribution.
3. **Lead with the empirical finding, not the tools.** The tools are how it was found.
4. **Drop the framing that today invented a new kind of agent.** It did not. It
   produced an unusually well-documented instance of a known failure mode, in a lab
   that caught it on itself and published the corrections within hours. That is a
   smaller claim and a far more defensible one.

## 5. What would make (a) and (c) genuinely strong

- Run PROBE E against instruments in a repository **we did not write**. n=1 codebase is
  an existence proof; the prevalence claim needs strangers' code.
- The memoryless-same-model control, already specified: if a fresh instance of the same
  model in author-role finds at adversarial rates, the mechanism is memorylessness
  rather than adversarial role — a better paper than the one we set out to write, and
  one that would cut against our own framing.
- Pre-register the defect classification **before** the passes run. Today's ledger was
  classified retrospectively, which is the failure we spent the day condemning.
