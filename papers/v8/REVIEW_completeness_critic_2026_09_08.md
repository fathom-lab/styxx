Fathom Lab · **A critic's pass, not a result.** Nothing here is measured. Every item is a reading of committed text against other committed text, and every item names the lines a reader can check without me.

**What it read.** `papers/v8/SPEC_v8_v0.1_draft_2026_09_07.md` (407 lines, the text as reviewed); `papers/v8/REVIEW_v8_spec_2026_09_07.md` (147 distinct findings — headings and titles enumerated, then read in full for every finding this pass challenges, plus the whole Refuted section and the whole Operator-decisions section); `papers/v8/SPEC_v8_v0.2_draft.md` (632 lines, the hand-written amendment nobody had checked); and, for two items, the repository state at `C:\Users\heyzo\clawd\wt\v8` (`git config extensions.objectFormat` unset; `git hash-object papers/v8/SPEC_v8_v0.2_draft.md` → `d3a7705a8ea6a22de5b8799446d101fecf36d5b0`, 40 hex).

**What the method could see.** Cross-section interaction: two rules each defensible alone and wrong together. **What the method could not see.** It did not run the system, did not write a cert, did not build a Merkle tree, did not implement an ambiguous rule twice. It did not read the whole ledger word for word — 147 findings at that length exceeds one context — so a duplicate is possible; each item below names the nearest existing ids and says why it is not them.

Section coverage of v0.1 is genuinely good: every numbered section and every appendix carries at least one standing finding, and the sections with the thinnest coverage (§3.3, §8.5) are three sentences of deferral that earn their silence. The gap is not sections. It is the seams between them, and it is v0.2.

### C-01 · blocker · v0.2 §2 (line 97), §2.6 (line 179), §8.2 (lines 417–425), §8.3 (line 430), amendment A-25 (line 37)
**A-25 announces a fix that the draft does not contain: `public` is still inside the signed envelope, and the file it was moved to does not exist in the storage layout — as written, every cert is rejected at append**

- mechanism: A-25 states the defect and the fix precisely — "`public` cannot live inside the signed envelope and also be 'computed at append, never set by the issuer' — the signature would break. `public` is log metadata beside the entry (`<index>.meta.json`, §8.2), not an envelope field; §2 and §2.6 read accordingly." Neither half landed. Line 97 still carries `"public":  true,` inside the envelope whose canonical bytes are digested by §2.1 (`D = sha256(JCS(cert with "id" and "sig" removed))` — `public` is not removed). Line 104 still says "`public` is computed at append (§2.6), never set by the issuer." §2.6 still says "Computed at append". And §8.2's layout lists `entries/`, `blobs/`, `sth/`, `keys/`, `README.md` — there is no `<index>.meta.json` anywhere in the document (grep: the string occurs once, in A-25 itself). So the issuer must choose a value for a field the spec forbids the issuer to set; CI (§8.3: "computes `public`") must write it; writing it changes the JCS bytes, changes `D`, changes `id`, and invalidates `sig`; §2.1 then rejects the cert with exit 4. The only escape an implementer has is to leave the issuer's value alone, which makes §2.6 and line 104 false and hands the issuer control of the compliance view's public/non-public split (§12 line 515).
- evidence: v0.2 lines 37, 97, 104, 108, 179, 417–425, 430.
- nearest existing findings: S4-21 (redaction laundering into the compliance view) and S4-27. Different: those are about redaction propagation in v0.1, which had no `public` field at all. This is a v0.2 build artifact, self-diagnosed in the ledger and then not performed.
- amendment: delete `"public"` from the §2 envelope block; delete the sentence in line 104; rewrite §2.6 as "Log metadata, not cert content: the log stores `public` in `entries/<...>/<index:08d>.meta.json` beside the entry file, computed at append from the cert and its transitive refs. It is not part of the entry bytes, is not covered by the leaf hash, and is recomputable by any mirror from the entries it holds." Add the `.meta.json` line to the §8.2 layout and state that a mirror recomputes rather than trusts it.

### C-02 · blocker · v0.2 header (line 3), §6.1 (line 356), §14 (line 556), A.1 (line 588); amendment A-01
**Entry #0 names a hash the repository cannot produce and the spec's own encoding rule rejects: `git_blob_sha256` in a SHA-1 repository**

- mechanism: A-01 claims "entry #0 is a `result` cert of kind `document` carrying the git blob hash, never a checkout hash", and §6.1 fixes the body as `{ path, commit, git_blob_sha256, eol: "lf" }`. The worktree is an ordinary SHA-1 object-format repository: `git config --get extensions.objectFormat` returns nothing (exit 1) and `git hash-object` returns 40 hex. There is no git blob sha256 to carry. A.1 requires "Hashes as `sha256:<64 lowercase hex>`; validators reject any other length or case", so the value git actually produces is rejected by the validator that must accept entry #0. Two readings remain and they differ in bytes: sha256 over the blob *object* (`blob <len>\0` + content, which no tool in this tree emits) or sha256 over the file bytes (which is not a git blob hash and which the field name denies). S0-02's amendment asked for both `git_blob_sha1` and `content_sha256 (LF-normalized UTF-8)`; v0.2 replaced them with one field that is neither. The document that the log's opening entry is supposed to bind cannot be bound.
- evidence: v0.2 lines 3, 12, 356, 556, 588; `git config --get extensions.objectFormat` (unset), `git hash-object papers/v8/SPEC_v8_v0.2_draft.md` → `d3a7705a8ea6a22de5b8799446d101fecf36d5b0`.
- nearest existing findings: S0-02, S8-06, S14-01 — all about entry #0 having no type and no defined byte string. Different: those are answered in principle by A-01 (a `document` result cert). This is that answer failing on its own terms, and it is checkable with one command.
- amendment: `document` body = `{ path, commit, git_blob_sha1, content_sha256, eol: "lf" }` with A.1 pinned: `content_sha256 = sha256(the file's bytes as committed, LF line endings, no trailing byte added)`; `git_blob_sha1` is the 40-hex git identifier carried as a plain string, explicitly exempt from A.1's `sha256:` form, and marked informative. ### C-03 · blocker · v0.2 §3.1 (lines 208, 214), §5.1 (lines 293–295), §5.3 (line 314), §2.1 (line 112), §8.3 (line 430); amendment A-15
**The sensitivity receipt and the floor each have to exist before the other: the canonical fingerprint cannot be appended, so no `same` verdict can ever be issued**

- mechanism: three rules written in three sections close a ring. (1) §3.1 puts `"sensitivity": "sha256:<sensitivity result id, §5.3>"` in the fingerprint body, and §5.3 requires that cert to be "referenced by every fingerprint that carries a floor". (2) A-09/§2.1: "A validator MUST resolve every entry in `refs` to a logged cert of the type its role names before accepting the cert", and §8.3's CI "resolves every ref" at append. So the canonical fingerprint (run 0, the cert that carries `noise_floor`, line 214) cannot be appended until the sensitivity result is in the log. (3) §5.3 defines the sensitivity result as, for each positive control, "the per-channel distance and whether it exceeded the floor" — a statement about the floor. The floor is `max(D_c)` over the pairwise distances of all R runs (§5.1 step 3), run 0 among them, and the only logged home of the floor is run 0's body. Three escapes, all defective: reference run 0 from the sensitivity cert and the ring is a hard append cycle; state the floor as a bare number in the sensitivity cert and the threshold has no receipt, which §0's own rule ("Anything that can't be reproduced from the cert is not a claim; it's a note") and §2.4's numeral-binding forbid; or compute the sensitivity against a floor over R−1 runs, in which case the receipt tests a threshold that is not the published one. Meanwhile §5.3's gate is unconditional: "A `same` without a sensitivity receipt is printed as `same (sensitivity unmeasured)` and exits 2." Appendix D step 4 therefore cannot return 0 for any cert, ever, and step 5 (which triggers on exceeding the floor) is never reached from a clean path.
- evidence: v0.2 lines 112, 208, 214, 293–295, 314, 430; App. D lines 629–631.
- nearest existing findings: S5-06 (a `same` ships with a measured null and no measured detection power) is the finding A-15 answers here; S2-15 (cert ids outside `refs`, append conditional on refs resolving) supplies the other half of the ring. Different: neither states the ordering, because in v0.1 there was no sensitivity cert and no refs-resolution rule at append. The defect is created by the two amendments meeting.
- amendment: break the ring on the direction that carries no evidence backwards. The sensitivity result references the noise-plan prereg and the R floor-run certs (roles `noise_plan`, `run`), recomputes `floor_c` from those runs itself, and records it; the canonical fingerprint does **not** reference the sensitivity result — clients resolve it by query (subject identity + `recipe_core` + `noise_plan` id), and §5.3's gate reads "verify refuses `same` unless it can find such a result in the log". Add to §5.1 a step 5 naming the append order: floor runs, then the sensitivity result, then the canonical fingerprint.

### C-08 · major · v0.2 §5.5 (line 321), §5.1 (lines 293–295), §6 (line 336), §12 (line 513), §8.3 (line 430)
**The baseline rule fires on the floor's own runs: each of R−1 runs must carry a `--diff` result that §6 guarantees exits 2, and every floor publishes R−1 change-tracking entries about a model that did not change**

- mechanism: §5.1 step 4 makes each floor run a logged fingerprint cert of the same subject under the same recipe. §5.5 then applies to each of them: "A fingerprint for a subject that already has a fingerprint under a comparable recipe in the log must reference the most recent such cert (role `previous`) and be accompanied, in the same submission, by a `verify --diff` result against it; append refuses a fingerprint that would silently start a new baseline." During floor construction no floor exists yet, and §6 rules that "`--diff A B` ... exits 2 if A has no floor". So building one floor requires R−1 diff results that are inconclusive by construction, and §12's change-tracking row shows "result (verify)" for the subject — the record of a model's stability is padded with R−1 entries that measured nothing. Second leg, and the more serious one: §5.5's predicate ("the most recent such cert in the log") is a function of log state at the moment of append, not of the cert's bytes. A mirror re-validating the same entry later, or a client checking a cert against a longer tree, cannot re-derive the acceptance decision from the bytes it holds. That is the property `styxx/charon.py` exists to hold — every verdict re-derived from bytes — and §5.5 is the one rule in v8 that breaks it.
- evidence: v0.2 lines 293–295, 321, 336, 430, 513.
- nearest existing finding: S5-08 (no canonical fingerprint, so an issuer moves the baseline) — §5.5 is verbatim its amendment. Different: nobody asked what the rule does to the R−1 certs the floor procedure itself creates, or noticed that it makes append acceptance a function of log state.
- amendment: scope §5.5 to canonical fingerprints only — "a fingerprint with `run_index` 0 that carries a floor"; exempt certs whose `refs` name the same `noise_plan` as an existing floor set. Restate the predicate as a property of bytes: the cert names its `previous` and the accompanying diff, and a validator checks that the named cert exists and that no *other* canonical fingerprint for the same (S_identity, recipe_core) sits between them in the log — a check any mirror can repeat, with the failure surfaced as a client-computed status (`baseline-gap`), not as an append refusal.

### C-10 · major · v0.2 §2 (lines 87–100), §2.1 (line 108), §6.1 (lines 351–356), §14 (line 552)
**No per-type field-presence rule exists, so `subject` and `recipe` on a `document`, `prereg`, `challenge`, `sublog` or `promotion` cert are absent for one implementer and empty objects for another — two ids for the same cert, and §14's independent-implementation gate is what will fail**

- mechanism: §2 shows one envelope with `subject` and `recipe` as members and says "One schema, eight types". Entry #0 is a `result` of kind `document` about a markdown file: it has no model subject and no recipe. A `sublog` cert has neither. A `challenge` carries its evidence in `refs`. The spec never states, for any type, which envelope members are required, forbidden, or optional. Under JCS an absent key and a key holding `{}` produce different bytes, hence different `D`, hence different `id` and a different leaf hash. This was judged editorial once (S2-07's refutation: "presence is already per-type by implication ... What survives is editorial"), and in v0.1 that was defensible. It is not defensible in v0.2, which (a) makes field presence load-bearing — §9's validity test reads `S_identity` "from the two certs", §2.6 walks transitive refs, §2.3 keys on `recipe_core` — and (b) makes agreement between two implementations a release condition: §14 weeks 1–4 requires "a second implementation in JavaScript, written from this spec without reading the Python, [that] agrees on the conformance vectors". A JS author reading §2 has no way to know whether entry #0 carries `"subject": {}` or nothing.
- evidence: v0.2 lines 87–100, 108, 351–356, 552; ledger, Refuted section, S2-07.
- nearest existing finding: S2-07 (refuted) and S2-09. Different: the refutation was correct for v0.1's stakes and is stale for v0.2's; and the specific harm — two content addresses for the same evidence, discovered by the ship gate — is named nowhere.
- amendment: add §2.7, a presence table: for each of the eight types, which of `subject`, `recipe`, `body`, `refs` are required, optional or forbidden, and the rule "a forbidden member is absent, never empty; an optional member that is absent is absent, never null". Put one vector per type in `conformance/v8/` before the JS implementation starts.

### C-11 · major · v0.2 §7.1 (lines 362–367), §2.2 (lines 119–142), §10 (line 472), §12 (line 512); amendment A-07

### C-13 · major · v0.2 §5.1 (line 294), §5.2 (line 311), §3.1 (line 208); amendment A-15
**`alpha_single` is printed per channel and the exit code is taken over five, so the number the cert publishes understates the size of the test that actually governs the verdict**

- mechanism: A-15 answers S5-03 by recording, per channel, "`alpha_single = 1/(pairs+1)`, the nominal probability under exchangeability that a fresh same-model run exceeds the max" — 1/11 ≈ 0.0909 at R = 5. The verdict is not per channel: §5.2's ladder is "`drift` if any channel is `drift`", a maximum over up to five channels, and there is no overall size anywhere in the cert or the printout. Under the spec's own exchangeability assumption, and treating channels as independent — which they are not, and the spec says nothing at all about their dependence, which is itself the gap — the pre-confirmation size of the overall test is 1 − (1 − 1/11)^5 ≈ 0.38, roughly four times the number the cert prints beside each channel. The confirmation run reduces it by a factor the spec does not state and cannot state without a dependence model. So the one statistical figure a reader is handed describes a test that is not the one producing the exit code.
- evidence: v0.2 lines 208, 294, 311; ledger S5-03 ("the spec states no error rate and applies no correction across five channels").
- nearest existing finding: S5-03 — this is the half of it A-15 did not perform. Different: S5-03's multiplicity clause was never amended; the amendment supplied the per-channel nominal size only.
- amendment: record `alpha_overall` in `noise_floor` beside the per-channel figures, computed by the same permutation logic over the channel set actually evaluated (the fraction of the R runs whose *maximum standardized* channel distance to the reference exceeds the observed one), and print it as the number that governs the exit code. State that the per-channel `alpha_single` is diagnostic. If the permutation is not implemented in 8.0, print "overall size unmeasured" and route `drift` through exit 2 until it is.

## Limits

- This pass challenges the amendment draft harder than the v0.1 text, because that is where the unexamined surface is. A reader who wants v0.1's own uncovered ground will not find much here beyond C-17's `item_id`; the ten lenses covered v0.1's sections well.
- Nothing here is measured. C-13's arithmetic is the spec's own `1/(pairs+1)` compounded across five channels under an independence assumption the spec does not make and that is probably false — the figure is an illustration of a missing number, not a claim about the false-drift rate.
- Two items (C-02's repository check) rest on the state of `C:\Users\heyzo\clawd\wt\v8` on 2026-09-08 and on no other checkout.
- The ledger was read by headings, titles, and full text for the findings challenged. 147 findings at that length exceeds one reading; a duplicate is possible. Each item names the nearest ids so a duplicate is cheap to detect and cheap to drop.
- No item here was written to fill a quota; where an area is covered, the pass says so and moves on. Severities follow the ledger's own scale, and the four items that turn on what two implementers would do (C-04, C-05, C-10, C-17) would be settled faster by writing the cert twice than by another reading pass. Nobody has yet written one.
