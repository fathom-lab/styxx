# SEALS — the digests the lab will anchor, as bytes in the tree before any anchor exists

Fathom Lab · 2026-09-13 · **no anchor exists yet.** This file states what a seal is, which
digests are to be sealed, and the rule that decides the digest — so that `git grep` finds the
frozen hash in the repository and not only in an operator's notes.

## the rule

A seal is the sha256 of the **git blob** of the frozen file — the bytes as git stores them, LF —
computed as `git show <commit>:<path> | sha256sum`. Never the working copy: on a Windows checkout
made before a `-text` pin lands, the working copy carries CRLF and hashes differently (measured
2026-09-13: working copy `b8b7fe6b…`, blob `b3b98710…`, same file, unchanged since freezing). An
operator who hashes the working copy either stops for nothing or seals a digest no stranger can
reproduce. The memo text is built by `python -m styxx.clock memo <kind> <digest>` and nothing
else; `styxx.clock` takes the digest as written and refuses to fold it.

A seal proves that the digest existed no later than the block's time. It does not order a run
relative to that time: nothing in the sealed run's inputs depends on the seal (the deploy-scale
run uses the hand-frozen 48 canaries by design). A run whose canary draw comes from the seal's
own beacon would carry that ordering; that is the next PREREG's job, not this one's.
That PREREG exists since 2026-09-14 (`PREREG_checksum_beacon_draw_2026_09_14.md`, anchor #6 below): its
block hash draws the 48 canaries of the run it governs, so WHICH 48 items that run grades is fixed
by a value no one could choose, after the seal. It does not order the computation: the pool is
public, a fingerprint scores items independently, and every item's value can be computed before any
seal and subset to whatever a beacon later names. (Corrected 2026-09-14, the day it was written: this
paragraph first said "that run cannot precede its seal and a stranger checks the order from the
bytes", which the lab's red team showed is false; `CORRECTION_prereg_beacon_draw_2026_09_14.md`,
anchor #6b, withdraws the same claim from the PREREG.)

## the earliest-memo rule (added the same night, tightened 2026-09-14)

A digest may be anchored more than once. Its seal is the **earliest** confirmed transaction that
the creator wallet **signed** and whose memo instruction is **exactly** `styxx <kind> <digest>`.
`python -m styxx.clock verify` enforces it by resolving every transaction the wallet's signature
listing shows carrying the digest: a recorded transaction that is not the earliest reads
`EARLIER_MEMO_EXISTS`, and the beacon belongs to the earliest one's slot. The listing also shows
transfers another key sent the wallet; a memo in one of those is listed as foreign and never seals.
Until commit `7ef0e7ac` the scan counted it, so anyone who read a digest in this file could have made
its seal read `EARLIER_MEMO_EXISTS`. A flood of such memos beyond what the scan resolves reads
`EARLIEST_UNKNOWN`: it can delay a run, it cannot choose a beacon. Anchor each digest once. If a
transaction fails and is resent, the failed one does not count (only confirmed memos seal), and the
record must name the confirmed one.
