RECEIPT v0 check

RECEIPT v0 is an unsigned draft. Fathom Lab wrote it; nothing in it is frozen, and nobody outside the lab implements, emits or checks these objects.

The checker in this page is lab-written. It is receipt/v0/check_v0.js, embedded byte for byte. It is not independent of the lab.

A HELD verdict says one comparison passed. It never says a sentence is true. Read the section on what the verdicts do not show before relying on one.

This page makes no connection of its own. Its Content-Security-Policy forbids connections in browsers that enforce it. The lab has not yet watched the page run in a browser. Some paths are outside any page's policy; the last section names them.

How this page reads your inputs

  • A chosen file is read as its exact bytes. For exactness, choose the file.
  • Pasted text is encoded as UTF-8. Browsers hand a text box to the page with every line end as LF (CR LF and a lone CR become LF), and a character that has no UTF-8 form (an unpaired surrogate) becomes U+FFFD. The page changes nothing else: no trimming, no Unicode normalisation, no added final line end. A pasted document can get a different verdict from its file, not only a different digest: a claim's length or a quoted needle can change with its line ends. Every result made from pasted text says so.
  • Each input shows its byte count and sha256, so you can compare them with sha256sum of your own file. Every result lists the byte count and sha256 of each input that run was given, with the name and commit label.
  • When an input, the name, the commit label or the mode changes, the result on screen is replaced by a line asking you to run again, and the answer of a run still in progress is dropped. While a chosen file is being read, run waits.
  • An empty box is no input. With no document the checker refuses (nothing_to_verify); to check an empty document, choose an empty file.
  • The document name is inside the digest (13.6): the same bytes under two names give two digests. Choosing a document file fills the name field from the file's name. The command line checker uses the path it was given unless it gets --name; give it --name with the same text to get the same digest.
  • Each run starts a fresh worker made from the embedded checker's text, with a limit of 10 seconds. If it hangs, fails, or answers with anything this page does not accept, the page says "no verdict" and why. If the browser cannot start a worker, nothing runs: the page never runs the checker without a time limit. Some documents take the lab's checker longer than 10 seconds (for example many lines that open a tag and never close it); the command line checker, which has no time limit, can still answer those.
  • The page takes a result whose receipt text has at most 2,000,000 characters; above that it says "no verdict: the result is too large for this page". It draws at most 200 span cards and the first 200,000 characters of the receipt; the copy button copies the whole receipt.
  • Direction control characters (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) in anything the page draws are shown as markers such as <U+202E>, so they cannot reverse the text after them. The copy buttons copy the raw text.

What the verdicts do not show

From RECEIPT_v0.md sections 12 and 14 (DRAFT, unsigned).

A HELD verdict does not show:

  1. That the sentence is true. HELD says one comparison passed: a printed number equals a named number at the printed precision; a quoted string occurs in named bytes; a stated hash equals the sha256 the manifest records (and the hash of the bytes, when the entry carries them); a string does not occur in bytes a harness called complete. The words around the number are not read: "Latency fell to r1's 240" holds if r1 says 240, whether or not anything fell.
  2. That the bytes are not the author's. The only authorship test reads the manifest. Bytes the author wrote that the harness never digested are not caught.
  3. That the manifest is honest. Nothing is signed. The rung is declared, not verified. A manifest minted by the author's own code passes every rule.
  4. That the right sentences were bound. The author chooses what to mark. A document can be SWORN-HELD on one trivial span beside any number of unbound claims. The counts are counts of what was marked, not of what mattered.
  5. That the receipt bytes mean what the sentence suggests. A number at a JSON pointer is a number at a JSON pointer; whether it is the quantity the sentence talks about is not checked.
  6. That the span was written before the evidence was seen, or at any particular time.
  7. That anything was checked, unless a row reads HELD or FAILED. MALFORMED and UNRESOLVED rows were not compared. SWORN-UNCHECKED is the word for that case.
  8. That another checker agrees. The text's two checkers, check_v0.py and check_v0.js, were both written by the lab, the second with the first open. A mistake they share is invisible to any comparison of the two. Agreement inside one lab is not agreement from outside it.
  9. That any evidence bytes were read. A hash span on an entry without bytes compares the sentence with the manifest's own string. A document whose every HELD row is such a span reads SWORN-HELD with no evidence byte opened.

One HELD span is enough for SWORN-HELD, whatever the number of UNRESOLVED spans beside it (13.11). REDERIVES says a receipt is what this checker computes; it does not say the document held.

RECEIPT v0 is a lab draft of a format, not a standard and not a specification anyone else has adopted. Nothing in it is claimed to be new: binding statements to digests of evidence is older than this lab. The checker checks bindings an author hands over. It does not find claims, and it does not detect false statements in prose.

No network

The page carries this Content-Security-Policy in a meta tag:

@@CSP_TEXT@@
  • default-src 'none': forbids every kind of load not named below: fetch, XMLHttpRequest, WebSocket, EventSource and sendBeacon connections, images, fonts, media, frames, objects and manifests.
  • script-src with one hash: only this page's one inline script may run. No other script, no code from strings, no event-handler attributes. The embedded checker sits in a non-running text/plain element and runs only in the worker.
  • style-src with one hash: only this page's one style block.
  • worker-src blob:: a worker may start only from a blob: URL, which the page makes from the checker's text. data: and network URLs are refused for workers.
  • base-uri 'none' and form-action 'none': default-src does not cover these; they forbid a base element and any form submission.
  • require-trusted-types-for 'script' and trusted-types receipt-v0-worker: where the browser implements Trusted Types, no string can become markup or a script URL; the one script URL allowed is the blob: URL the page has just made for the worker.

The CSP Level 3 specification says a worker made from a blob: URL inherits the policy of the page that made it, so the ban on connections should apply inside the worker too. That is the specification's rule; the lab has not tested it in a browser. As a second layer, before it reads any input the worker removes fetch, XMLHttpRequest, WebSocket, EventSource, importScripts, FontFace, fonts and similar globals. That layer is modest: it cannot remove import(), which is syntax, and it runs after the checker's own top-level code; both are left to the inherited policy. The page's own script makes no connection: it has no links, no images, no forms and no outside resource of any kind.

What no page policy stops:

  • browser extensions that can read the page and its text boxes;
  • the browser's page translation, which in some browsers sends the page's text to a service (this page asks browsers not to offer it, with translate="no", which not every browser honours);
  • clipboard sync by your operating system after you press a copy button;
  • navigation you start yourself: a link or a file dropped onto the page, the address bar;
  • a favicon request the browser may make on its own when the page is served over the web (it carries none of your inputs).
